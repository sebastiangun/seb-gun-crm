seb_gun CRM v28.20 — наблюдаемость, дизайн контрольных разделов и исторический аудит

Что исправлено
==============

1. Менеджеры / SLA: быстрый отчёт без зависания HTTP
----------------------------------------------------
Раньше GET /api/sla/report прямо внутри HTTP-запроса ходил в VK, перечитывал диалоги и синхронизировал журнал. На Render Free это могло занимать слишком долго и приводить к net::ERR_CONNECTION_RESET.

Теперь:
- /api/sla/report строится сразу из PostgreSQL;
- свежая синхронизация VK запускается фоном и не блокирует страницу;
- GET автоматически повторяется один раз при сетевом обрыве;
- при временной ошибке прежние данные на экране не обнуляются;
- показывается время последнего успешного обновления и состояние фоновой синхронизации.

2. Первичная проверка диалогов: убран скрытый предел 10 000
-----------------------------------------------------------
Раньше bootstrap использовал maxPages=50 * 200 диалогов = максимум 10 000. На скриншоте как раз было 10000, поэтому это мог быть не реальный итог, а потолок.

Теперь одноразовая проверка использует все страницы, которые сообщает VK, с аварийным верхним пределом 100 000 диалогов. Прогресс и количество ошибок сохраняются в PostgreSQL. После completed полный исторический scan при обычном запуске не повторяется.

3. Менеджеры / SLA: понятный интерфейс вместо нулей и кружка
-------------------------------------------------------------
Добавлено:
- прогресс первичной проверки в процентах;
- обработано / всего;
- количество ошибок;
- папки «Все / Нарушения / Вовремя / Ждут ответа» с числами;
- сводка «Всего / Вовремя / Нарушений / Ждут»;
- карточки по менеджерам;
- пояснение, как определяется нарушение;
- источник данных PostgreSQL и состояние фонового обновления;
- нормальные компактные переключатели дней недели.

4. История уведомлений: старые события до появления раздела
-----------------------------------------------------------
В v28.19 появилась таблица фактической доставки notification_history. Поэтому невозможно честно доказать, куда именно ушло Telegram/browser-уведомление до появления этого журнала.

v28.20 восстанавливает из старого SLA-журнала исторические СОБЫТИЯ:
- предупреждение SLA;
- нарушение SLA;
- доступные старые зависшие исходящие сообщения.

Такие строки имеют специальную метку «История до журнала» и явно показывают:
- событие действительно следует из сохранённой истории SLA;
- получатель старого уведомления не зафиксирован;
- Telegram: данных нет;
- браузер: данных нет;
- нельзя выдавать восстановленную строку за подтверждённую доставку.

Backfill идёт небольшими пакетами после окончания первичной проверки, чтобы не перегружать Render. Прогресс отображается в интерфейсе.

5. История уведомлений: сохранность
-----------------------------------
- исторически восстановленные строки автоматически не удаляются;
- фактические попытки доставки хранятся до 365 дней вместо 90;
- отображаются фактические / восстановленные / доставленные / частичные / ошибки;
- отдельные фильтры по получателю, менеджеру лида, CRM-статусу, событию, каналу, результату и дате.

6. Неотправленные сообщения
---------------------------
Добавлено:
- всего активных;
- сколько уже считаются зависшими по порогу;
- сколько с ошибкой;
- по скольким уже было уведомление;
- явное описание серверного watchdog;
- ошибки загрузки не маскируются пустым списком.

7. Настройка уведомлений
------------------------
На странице теперь есть живое описание текущего правила:
- сколько менеджеров выбрано;
- сколько CRM-статусов выбрано;
- какие события включены;
- рабочие дни и часы МСК;
- Telegram подключён или нет;
- браузер разрешён или нет;
- когда была последняя проверка.

8. «Ещё» и админка
------------------
- кнопки контрольных разделов получили нормальный компактный дизайн;
- первичная проверка показывает процент, числа, ошибки и папки;
- история уведомлений показывает количество записей;
- в админке «Нарушения» отображается нормальный прогресс и статистика, а не только running/число;
- сохранены удаление и восстановление нарушений.

9. Ошибка VM8 reportAllChanges / startTime
-------------------------------------------
В исходниках CRM нет reportAllChanges. Стек VM8:<anonymous> относится к внедрённому браузерному/extension-скрипту и не является ошибкой server.js/Vue CRM.
Реальная ошибка CRM из показанного лога — /api/sla/report net::ERR_CONNECTION_RESET — исправлена архитектурно (см. пункт 1).

Render
======
Текущий вручную сохранённый Build Command можно НЕ менять:
cd seb_gun_crm_render_ready && npm ci --include=dev && npm run build && npm run check:runtime && npm run test:v2819 && npm run test:database

В v28.20 script test:v2819 запускает и совместимость v28.19, и новый integration-v2820.js. Поэтому Render автоматически проверит новую версию даже со старым именем команды.

Проверено локально
==================
- node --check server.js — OK
- npm run check:runtime — OK
- npm run test:v2819 — OK (включает v28.20)
- tests/create-safety.js — PASS
- tests/phrase-source.js — PASS

Полный Vite build и postgres-storage test локально в этой среде не запускались из-за неполной установки npm-зависимостей после таймаута npm ci. На Render npm ci выполняется заново; предыдущий v28.19 там успешно собирался.
