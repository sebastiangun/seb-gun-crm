При подключённом PostgreSQL фразы обновляются однократно при запуске через `data/phrase-update.json`. Не затрагиваются журнал и сессии; не указанные в обновлении фразы базы остаются. При режиме JSON используется обновлённый `data/quick_phrases.json`.

Проверка базы: откройте `/api/health`. `database.mode = postgresql` и `database.ready = true` означают успешный запрос к PostgreSQL. `mode = json` означает, что PostgreSQL не подключён. HTTP 200 без просмотра тела этого не доказывает. Успешное соединение не подтверждает перенос старой истории: отдельно проверьте журнал, `npm run db:status` и сохранение настройки после перезапуска.

В логе теперь явно выводится `[storage] PostgreSQL подключён; таблицы готовы` либо `[storage] JSON — PostgreSQL НЕ подключён`.

# seb_gun CRM 28.16 — переход на PostgreSQL

Это изменённый проект из вашего ZIP 28.15. BlueSales остаётся основной CRM, VK — источником переписки. PostgreSQL хранит собственные настройки, журнал, аудит, сессии и локальные копии наблюдаемых карточек. База на вашем Render ещё не создана и рабочие данные туда ещё не перенесены.

## 1. Сначала сохранить текущие данные

**Не обновляйте действующий Render до экспорта истории.** В присланном архиве `data/notification-settings.json` содержит 0 записей журнала и 0 правил. Это не резервная копия работающего сервера.

Лучший вариант — забрать весь действующий каталог `data` через доступную консоль/резервное копирование сервиса и сохранить отдельно. Там находятся также изменённые фразы, права и цвета. Не публикуйте рабочие данные в открытый GitHub.

Если файловая консоль недоступна, для журнала и Telegram есть браузерный экспорт:

1. На компьютере откройте действующую CRM и войдите администратором.
2. Откройте F12 → Console.
3. Скопируйте и выполните содержимое `scripts/export-live-journal.browser.js`.
4. Сохранится `notification-settings.json`. Проверьте количество записей, указанное после экспорта.
5. Скопируйте папку `data` из этого проекта в отдельную папку, например `recovered-data`, и замените в ней `notification-settings.json` экспортированным файлом.

Этот браузерный экспорт включает доступный журнал и правила Telegram, но не исходящую очередь, удалённые записи, текущие фразы, права, цвета или старые сессии. Для их точного переноса нужен полный действующий `data`. Экспорт не восстанавливает историю, которой уже нет на сервере. Во время финального экспорта и переключения приостановите работу менеджеров, чтобы новые записи не остались в старом хранилище.

## 2. Создать PostgreSQL

В Render создайте Postgres в том же регионе, что `seb-gun-crm`. Перед созданием проверьте стоимость, срок хранения и резервное копирование выбранного тарифа. Для постоянной рабочей базы не выбирайте вариант с истечением срока. Сам проект не создаёт платных ресурсов.

Сохраните Internal Database URL для сервиса Render. Для импорта с вашего компьютера используйте External Database URL с TLS. Не присылайте URL с паролем в чат и не добавляйте его в GitHub.

Документация: https://render.com/docs/postgresql-creating-connecting

## 3. Перенести данные с компьютера

Требуется Node.js 22. Откройте терминал в `seb_gun_crm_render_ready`:

```sh
npm ci --include=dev
```

Создайте локальный файл `.env.local` (он исключён из Git) со значениями:

```dotenv
DATABASE_URL=External_Database_URL_из_Render
PG_SSL=1
```

Здесь строка — образец: замените её настоящим адресом. Проверка TLS-сертификата включена. Для провайдера с собственным CA задайте `PG_SSL_CA`; не отключайте проверку сертификата.

Выполните:

```sh
npm run db:migrate
npm run db:import -- /полный/путь/к/recovered-data
npm run db:status
```

В Windows путь с пробелами заключайте в кавычки. Импорт одной транзакцией создаёт записи и переносит JSON. Повторный запуск сообщает `alreadyImported: true`; существующие строки не перезаписываются. Ошибка разбора JSON отменяет импорт до первой записи.

**Импортируйте именно восстановленный каталог.** Не импортируйте сначала пустой журнал из ZIP: отметка об успешной миграции преднамеренно запрещает автоматический повторный импорт. Исправление ошибочного импорта выполняется отдельно после резервной копии и сравнения данных. Исходные файлы сохраняются.

Если перенос старой истории вам не нужен, можно осознанно импортировать комплектный `data`, но он не содержит рабочих лидов.

## 4. Настроить сервис и обновить GitHub

В Render → сервис `seb-gun-crm` → Environment задайте:

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | Internal Database URL вашей базы |
| `REQUIRE_DATABASE` | `1` |
| `SESSION_SECRET` | постоянный случайный секрет не короче 32 символов |
| `DB_IMPORT_ON_START` | `0` после ручного импорта |

Секрет можно сгенерировать локально командой `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Храните его в Environment. Смена секрета завершит существующие сессии. Старые cookies 28.15 при переходе на PostgreSQL потребуют повторного входа.

На внутреннем соединении Render не переносите локальное `PG_SSL=1` автоматически: используйте настройки TLS, соответствующие адресу провайдера. Все старые переменные BlueSales, VK и Telegram сохраните.

В репозитории замените содержимое папки `seb_gun_crm_render_ready` файлами из архива. Не создавайте вложенную папку с таким же именем. Путь Blueprint остаётся `seb_gun_crm_render_ready/render.yaml`. Не загружайте `.env.local`, `node_modules` и восстановленные рабочие данные.

Схема создаётся до начала обслуживания запросов. При `REQUIRE_DATABASE=1` отсутствие базы не переключает сервер на временные JSON. При ошибке подключения запуск останавливается; ошибки базы во время работы возвращаются как ошибки, а не ложное сохранение.

## 5. Проверить после запуска

- `/api/health` должен вернуть `database: {mode: "postgresql", ready: true}`.
- Войдите заново. Проверьте журнал и правила Telegram.
- В «Ещё» администратору доступна кнопка «Синхронизировать клиентов». Она переносит карточки, доступные текущему аккаунту BlueSales, и даты контактов. При большом количестве карточек запрос может длиться дольше таймаута браузера; уже записанные страницы сохраняются, повторный запуск безопасен.
- Карточки также сохраняются при обычном чтении BlueSales. Это наблюдаемый снимок, а не полная замена API и не автоматическое удаление исчезнувших карточек.
- Сохраните настройку, обновите страницу, затем перезапустите сервис и убедитесь, что запись осталась.
- Создайте одного тестового клиента. Проверьте менеджера текущего аккаунта, статус «Запустил воронку» и отсутствие дубля при повторном нажатии.

## Что изменено

- `customers.addMany` заменён на `customers.add`. Менеджер и статус включены в первоначальный запрос.
- При недоступной проверке VK ID создание не отправляется. При таймауте операции записи транспорт автоматически не повторяет запрос.
- Попытка создания записывается в PostgreSQL **до** внешнего вызова; неопределённая попытка не истекает сама. Если карточка не находится, нужна проверка администратором. Это сознательно безопаснее повторного создания. Удалять запись `customer_create_requests` можно только после достоверной проверки отсутствия карточки в BlueSales; автоматического сброса нет.
- Журнал хранится отдельными строками. Независимые изменения объединяются; конфликтующие изменения возвращают 409 вместо тихого затирания.
- Аудит хранит изменения записей и наблюдаемую смену менеджеров. Удаление из интерфейса скрывает запись, сохраняя аудит.
- Рабочие дни и порог нарушения добавлены к существующим настройкам «Ещё → Telegram и уведомления». По умолчанию 8 минут на предупреждение, более 20 на нарушение; все дни рабочие, чтобы сохранить поведение предыдущей версии. Ночная смена относится к дню её начала.
- В журнале есть фильтр «Нарушения», включая уже отвеченные обращения. SQL хранит первую фиксацию нарушения. Назначение ответственного основано на наблюдаемой истории, а не достоверном времени внешней смены менеджера, если API его не предоставил.
- Постоянные сессии используют случайный cookie; зашифрованный снимок хранится в БД. Выход удаляет сессию из БД.
- Фразы, настройки доступа, цвета и UI-профили сохраняются в БД; успешный ответ следует после записи.

## Ограничения и проверка

База устраняет зависимость этих данных от локального диска Render. Она не гарантирует отсутствие 502 от BlueSales/VK и не предотвращает сон бесплатного веб-сервиса. Таймер внутри спящего сервиса не обеспечивает уведомление точно через 8 минут: требуется постоянно работающий сервер либо внешний вызов существующего защищённого планировщика.

Полная переписка продолжает читаться из VK; существующие ограничения выборки сообщений и синхронизации истории остаются. PostgreSQL сохраняет то, что CRM увидела, а не восстанавливает неизвестные сообщения. Кэш расшифровок голосовых и временные аудиофайлы по-прежнему локальные. Просмотр журнала пока читает все его строки; для большого объёма следующим этапом нужна серверная пагинация. Проект рассчитан на одну организацию BlueSales и одно сообщество VK на развёртывание.

Ошибка `startTime` не подавляется: по одному сообщению её происхождение нельзя доказать. Причины сетевых обрывов требуют логов сервера.

Проверены сборка Vue, актуальные проверки из Blueprint, сценарии создания с имитацией внешнего API и SQL-сценарии на PGlite (PostgreSQL в WASM): повторный импорт, параллельные снимки, конфликт и откат, сохранение аудита, сессии и календарь. В PGlite-тесте advisory locks заменены заглушкой: сетевой пул, TLS и блокировки нескольких серверных процессов там не проверяются. Живые BlueSales/VK и ваша облачная база в этой среде не подключены.

```sh
npm run check
npm run test:database
```

Для резервных копий рабочей PostgreSQL используйте резервирование провайдера или `pg_dump`; проверьте восстановление на отдельной базе. Откат к 28.15 не умеет читать PostgreSQL — сначала потребуется экспорт новых данных обратно, иначе старая версия покажет прежнее состояние JSON.
