seb_gun CRM v28.19 — ONE-TIME DIALOG BOOTSTRAP + ADMIN SLA + NOTIFICATION AUDIT

Что изменено

1. Первичная проверка всех диалогов — один раз
- После авторизации сервер автоматически запускает историческую проверку VK-диалогов.
- Обрабатывается до 10 000 диалогов (50 страниц по 200).
- Для каждого диалога анализируются до 200 последних сообщений и создаются эпизоды SLA.
- Диалоги раскладываются в папки: «Нарушения», «Вовремя», «Ждут ответа», «Все».
- Прогресс и отметка completed сохраняются в PostgreSQL через app_documents.
- После completed полный исторический проход при обычных следующих запусках больше не выполняется.
- Если Render перезапустился посреди первичной проверки, процесс продолжится с последнего сохранённого пакета, а не с начала.
- Текущий контроль новых неотвеченных сообщений продолжает работать — это не повтор исторического сканирования.

2. История SLA стала устойчивее
- У эпизода сохраняется снимок SLA/графика, который действовал при его регистрации.
- Позднее изменение настроек не переписывает старое нарушение задним числом.
- Сохраняются менеджер, CRM-статус, их история, время получения, ответа и ответственный на момент нарушения.

3. Админка → «Нарушения»
- Администратор видит текущие нарушения отдельно.
- Можно открыть диалог.
- Можно удалить нарушение из статистики.
- Удалённые записи можно восстановить (при PostgreSQL исходная строка остаётся в таблице, удаление работает через tombstone).
- В админке виден статус первичной проверки и количество записей по папкам.

4. Разделы полностью разделены
- «Неотправленные» — только очередь исходящих и серверный watchdog.
- «Менеджеры и SLA» — время ответа, вовремя/нарушения/ожидание и статистика.
- «Настройка уведомлений» — только получатель, менеджеры, статусы, дни, часы, тип события и каналы.
- «Уведомления» — отдельная история фактической доставки.

5. Серверный watchdog зависших исходящих
- Настраивается отдельный порог «считать зависшим через N минут».
- Не зависит от SLA времени ответа менеджера.
- После порога создаётся событие outbox_stuck.
- Применяется тот же строгий фильтр менеджер + CRM-статус + рабочие дни/время.
- Поддерживаются Telegram и браузерная плашка.
- Есть защита от дублей; повтор задаётся отдельным интервалом.

6. История уведомлений
Для каждой попытки фиксируются:
- тип события: предупреждение SLA / нарушение / зависшее исходящее;
- клиент и VK peer_id;
- получатель уведомления;
- менеджер лида;
- CRM-статус;
- дата и время МСК;
- снимок фильтра (менеджеры, статусы, дни, период, SLA);
- Telegram: доставлено / ошибка / не подключено;
- браузер: ожидает / доставлено / ошибка / запрещено / не получено;
- общий результат: отправлено / частично / ожидает / не отправлено.

Фильтры истории: поиск, получатель, менеджер лида, CRM-статус, событие, канал, результат, дата от/до.

7. PostgreSQL
Добавлена таблица notification_history. История доставки хранится отдельно от lead_journal, sla_violations и очереди.
