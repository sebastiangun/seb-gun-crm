seb_gun CRM v28.21 — защита Render/VK от перегрузки 429/503
============================================================

Почему появились ошибки
-----------------------
1. v28.20 запускал одноразовую историческую проверку слишком агрессивно:
   - сначала загружался большой список диалогов;
   - история читалась по 4 диалога параллельно через Promise.all;
   - после каждых 4 диалогов целый notification-store сравнивался/сохранялся в PostgreSQL;
   - между пакетами было всего 220 мс.
   Это одновременно давило на VK API, PostgreSQL и бесплатный Render.

2. Интерфейс сам создавал лишние запросы:
   - App.vue мог дважды вызвать POST /api/bootstrap/dialogs-once после авторизации;
   - Менеджеры опрашивали bootstrap каждые 2.5 сек и периодически одновременно запрашивали SLA;
   - История уведомлений опрашивалась каждые 3.5 сек;
   - Ещё каждые 3 сек одновременно запрашивал bootstrap и тяжёлую историю уведомлений.

3. GET /api/notifications/history не был обычным чтением: каждый запрос запускал пакет исторического backfill и затем запись store обратно в PostgreSQL.

4. Из-за перегрузки Render начинал отвечать 503/429 уже не только API, но и статическим файлам.
   Поэтому CSS мог получить HTML-страницу Render с ошибкой 429, после чего Chrome писал:
   Refused to apply style ... MIME type ('text/html').
   Это следствие 429, а не проблема CSS-файла.

Что изменено
------------
- Один запуск bootstrap из App вместо двух.
- Историческая проверка теперь идёт постранично, а не держит весь архив в памяти.
- История VK читается последовательно с минимальным интервалом ~450 мс.
- VK error_code=6 получает exponential backoff; после серии ограничений scan ставится на паузу и автоматически продолжается.
- Прогресс сохраняется; после рестарта продолжается с currentBatchEnd.
- Snapshot PostgreSQL сохраняется каждые 25 обработанных диалогов, а не каждые 4.
- SLA bootstrap polling: примерно раз в 12 сек, отчёт обновляется значительно реже; при 429/503 интервал увеличивается до 60 сек.
- История уведомлений polling: 15 сек с backoff вместо 3.5 сек.
- Экран «Ещё»: bootstrap 15 сек, история уведомлений только примерно раз в минуту вместо двух запросов каждые 3 сек.
- GET API получил общий cooldown/backoff для 429/502/503/504 и поддержку Retry-After.
- Исторический notification backfill перенесён из синхронного GET в фоновую очередь небольшими пакетами.
- /api/sla/report отдаёт максимум 2000 последних строк, но общую статистику считает по всей истории.
- /api/notifications/history отдаёт максимум 1500 последних строк, summary считает по всей истории.
- UI честно показывает, если список ограничен для производительности.
- Хэшированные Vite assets получают immutable cache на год, чтобы при обновлениях страницы меньше нагружать Render.
- Добавлены понятные сообщения «сервер временно занят / ограничил частоту», а уже загруженные данные не стираются.

Состояния первичной проверки
----------------------------
pending            — ещё не запущена
starting           — готовится
running            — идёт обработка
paused_rate_limit  — VK временно ограничил частоту; будет автоматическое продолжение
completed          — полная историческая проверка завершена; повторно обычным запуском не выполняется
failed             — ошибка, требующая просмотра lastError

Важно
-----
VM*: reportAllChanges/startTime по-прежнему не относится к CRM: такого кода в проекте нет.
Реальные ошибки этого случая: 503/429 и MIME text/html для CSS, вызванные перегрузкой/ограничением запросов.

Render Build Command менять не нужно:
cd seb_gun_crm_render_ready && npm ci --include=dev && npm run build && npm run check:runtime && npm run test:v2819 && npm run test:database

В v28.21 npm run test:v2819 также запускает integration-v2821.js.
